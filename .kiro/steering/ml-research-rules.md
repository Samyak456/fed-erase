# FedErase — ML Research Rules

These rules govern all machine learning and research algorithmic decisions in FedErase.
They exist to prevent the project from making scientifically unsupported claims.

---

## Rule 1 — The Scientific Position is Non-Negotiable

The following statement applies to the entire codebase, all documentation, all API responses,
all log messages, and all dashboard UI text:

> **FedErase estimates and mitigates a target client's learned contribution and evaluates
> the resulting model against a reference model trained without that client.
> It does NOT guarantee exact removal of all knowledge from the model.**

Any code comment, docstring, variable name, metric name, or UI label that implies exact
machine unlearning is incorrect and must be changed.

**Permitted language:**
- "mitigates"
- "estimates influence"
- "approximate unlearning"
- "contribution correction"
- "forgetting metric"
- "behavioral divergence from reference"

**Prohibited language:**
- "guarantees deletion"
- "exact unlearning"
- "fully erased"
- "removed from the model"
- "provably forgotten"

---

## Rule 2 — Document Every Algorithmic Assumption

Every algorithm or formula that affects unlearning validity must be documented in
`docs/algorithm.md` before implementation. The documentation must include:

1. Mathematical formulation (even if approximate).
2. The assumption being made.
3. The known limitations of that assumption.
4. Which configuration parameters control the behaviour.
5. The experimental conditions under which the assumption is more or less valid.

If you cannot document the assumption, you cannot implement the algorithm.

---

## Rule 3 — All Hyperparameters are Configurable

The following values must NEVER be hard-coded:

- Learning rate
- Number of FL rounds
- Number of repair rounds
- Lambda (contribution correction weight)
- Influence estimation weights (w1, w2, w3, w4)
- Strategy selection thresholds
- Dirichlet alpha
- Number of clients
- Batch size
- Epochs per round
- Minimum sample count for eligibility
- Maximum wait time for scheduling

These must be defined in `experiments/configs/*.yaml` or in a Pydantic settings class.

---

## Rule 4 — Never Fabricate Results

- Do not hard-code expected accuracy values.
- Do not skip evaluation steps.
- Do not report metrics that were not actually computed.
- If an evaluation step fails, the experiment must fail and log the failure — not silently proceed.
- Comparison tables must be generated by the actual experiment system.

---

## Rule 5 — Maintain a Clean Conceptual Separation

The following concepts are distinct and must not be conflated in code or documentation:

| Concept | Definition |
|---------|-----------|
| **Federated Learning** | Collaborative training across clients without raw data sharing |
| **Contribution Tracking** | Recording lightweight metadata about each client's update per round |
| **Contribution Estimation** | Computing summary statistics from tracked metadata |
| **Influence Estimation** | Computing a heuristic score of how much a client affected the model |
| **Unlearning** | Modifying the model to mitigate a target client's contribution |
| **Repair Training** | Running additional FL rounds with remaining clients after unlearning |
| **Forgetting Verification** | Measuring how much the unlearned model diverges from the reference |
| **Resource Measurement** | Recording actual or simulated computation, communication, and storage costs |

Do not merge these into a single class or function. Each concept has its own module.

---

## Rule 6 — Influence Scores are Heuristics

The composite influence score (`I_i`) is a **heuristic** for strategy selection.
It is not a theoretically validated importance measure like a Shapley value or
an exact influence function in the sense of Koh & Liang (2017).

When surfacing influence scores in the API or dashboard, always label them as:
`"heuristic_influence_score"` — never `"exact_influence"` or `"data_contribution_value"`.

---

## Rule 7 — Full Retraining is the Gold Standard

The full-retraining reference (Phase 5) is the ground truth for all comparisons.
FedErase is evaluated against it — not against its own claimed correctness.

The full-retraining module must:
- Be independently executable.
- Store its own checkpoints separately from FedErase results.
- Record its own computation cost, communication cost, and accuracy.
- Never be modified to make FedErase look better by comparison.

---

## Rule 8 — Resource Profiles are Simulated

In development and simulation mode, client resource profiles (CPU count, RAM, GPU availability)
are **configuration values**, not actual hardware measurements.

Code and documentation must clearly distinguish:
- `simulated_resource_profile` — from config
- `measured_resource_usage` — from `psutil` or equivalent at runtime

Never claim the system measured something it did not measure.

---

## Rule 9 — Membership Inference Evaluation is Optional and Clearly Labelled

If a membership-inference-style evaluation is implemented:
- It must be in `evaluation/privacy.py`.
- It must be clearly labelled as an **approximate privacy proxy**, not a certified privacy guarantee.
- It must not be described as a formal differential privacy proof.

---

## Rule 10 — Experiment Reproducibility

Every experiment must:
- Set a global random seed (Python `random`, NumPy, PyTorch).
- Record the seed in the experiment metadata.
- Record the exact configuration file used.
- Record the software versions (Python, PyTorch, Flower).
- Produce results that can be reproduced by re-running with the same config and seed.

Experiments that are not reproducible are not valid for research comparison.

---

## Rule 11 — Do Not Modify the Algorithm Without Documentation

If any of the following are changed after initial implementation, a corresponding update
to `docs/algorithm.md` and the experiment configuration changelog is required:

- Influence estimation formula
- Strategy selection thresholds
- Contribution correction formula
- Repair training procedure
- Forgetting metric definition

Silent algorithmic changes invalidate prior experimental results.
